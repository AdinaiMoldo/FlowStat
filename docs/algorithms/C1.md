# C1. DSL compiler

Increment: I1 (phases 0-3, parser, shape validator), I4 (phase 4). One page when the function is finished.

## Two levels

- **Level 1 (known algorithm, our transformation):** Expression lexer and parser (precedence climbing) with error nodes and synchronisation tokens; table-driven document shape validator with did-you-mean (Levenshtein <= 2).
- **Level 2 (built on the output of level 1):** Semantic phases over the parsed tree: foreach expansion with a source map, then Tarjan SCC and shortest-cycle BFS on the expanded graph, ancestor bitsets, type inference with structural subtyping.
- **Dependence:** Level 2 runs on the tree and the diagnostics of level 1; a parse that stopped at the first error would hide every semantic error behind it.
- **Baseline for the benchmark:** A parser that stops at the first error, against ours: errors reported per run on the 30+ invalid workflows.

## Problem

Turn the text of a workflow into a plan (a static graph of step instances) or into diagnostics
that a designer can act on: all errors at once, each with a line and a column in the original file,
including errors in steps that exist only after `foreach` is expanded.

## Why a library does not solve it

A YAML parser gives a tree without meaning. A JSON-schema library would check the shape but cannot
give "did you mean", cannot expand `foreach` with a source map, and cannot parse the expression
language. A parser generator (Lark) would parse expressions but stops at the first error. The
phases here need the positions of the YAML tree, the catalogue and the expression trees at the same
time, so they are written as one pipeline over our own tree types.

## What is borrowed (textbook algorithms, named)

- Recursive descent with precedence climbing (expression parser).
- Tarjan's strongly connected components, breadth-first search, Kahn's topological order.
- Levenshtein edit distance.
- YAML text reading: `ruamel.yaml` (B1), the only third-party import in this package family.

## What is ours (the transformation and the code we write)

Level 1 (`dsl/`): lexer with positions that never raises; parser with error nodes and
synchronisation tokens; template splitter; table-driven shape validator with did-you-mean.
Level 2 (`compiler/`): foreach expansion with a source map; resolution of `needs` and `${...}`
to instances (`load[region]` to the instance of the same item, `check[*]` to all instances);
shortest-cycle reporting; ancestor bitsets used to prove that every step a step reads from is
guaranteed to run before it.

## Adaptation: where the plain textbook version is wrong

- A depth-first search reports *a* cycle, whichever it closes first. With `a -> b -> c -> d -> a`
  and `a -> e -> a`, the plain answer can be the four-step cycle; the designer needs the two-step
  one. We run a breadth-first search from every node of the component and keep the shortest.
  Test: `test_the_plain_textbook_answer_is_not_the_shortest_cycle` and
  `test_the_shortest_cycle_is_reported_not_the_first_found`.
- A parser that stops at the first error shows one error per run. Ours inserts an error node and
  goes on at the next synchronisation token. Test: `test_all_syntax_errors_are_reported_in_one_run`.
- Tarjan written with recursion fails on a chain of tens of thousands of steps in Python; ours uses
  an explicit stack. Test: `test_scc_does_not_recurse_on_a_long_chain` (20,000 nodes).
- Textbook precedence climbing has no rule for `not` between `and` and comparison, or for
  non-chaining comparison; both are added and tested against Python on 3,000 random expressions.

## Complexity

Lexer and parser: linear in the length of the text. Shape validator: linear in the size of the
tree, plus an edit-distance computation per unknown key. Expansion: linear in the number of
instances times the references per instance. Tarjan: O(V + E). Shortest cycle: O(V * (V + E)) per
component, which only runs on a component that already has a cycle. Ancestor bitsets: one OR per
edge on integers of V bits.

## Oracle (independent check)

- Graph algorithms: naive reachability and enumeration of all simple cycles on 400 to 500 random
  graphs each (`tests/unit/compiler/test_graph.py`); this found a real bug (stopping the cycle
  search at the first 2-cycle although a self-loop was shorter).
- Expressions: Python's own `eval` on 3,000 generated arithmetic and boolean expressions.
- Parser round trip: parse, print, parse again gives the same tree.
- Shape validator and compiler: 50 and 21 golden documents with exact line and column (37 and 19 when this card was written; counted again in M9).
- Crash resistance: 3,000 random token strings through the parser and 400 mutated copies of the
  main example through the compiler; the result is always a plan or diagnostics.

## Measurement

`docs/research/compile-time.md`: 200 steps in 161 ms (target 1 s); about 5,000 lines in about
0.7 s (target 3 s); time grows roughly linearly with the number of lines.

## Stated limits

- References are recognised in top-level scalar values of `with`; a reference inside a nested
  mapping or list value of `with` is kept as text.
- A goal cannot name a `foreach` step (E-REF-009).
- YAML anchors and aliases are rejected (E-YAML-004).
- Columns inside a double-quoted string that contains escape sequences can be off by the number of
  escapes before the position.
- Type inference (phase 4) is not part of M1; it is built in M5.
