# C6. Predicate solver and test generator

Increment: I4. Finished in M4 (5 November 2026).

## Two levels

- **Level 1 (known algorithm, our transformation):** Difference-graph solver: Bellman-Ford with (constant, strict) edge weights over a DNF with a clause cap; witness values from shortest-path distances.
- **Level 2 (built on the output of level 1):** Test generator: set cover (greedy, then exact search) over the targets "step runs" and "step is skipped" that level 1 has not proved impossible, with the candidate inputs taken from level 1's witnesses.
- **Dependence:** Level 2 needs the proofs and witnesses of level 1; without them it would emit tests for unreachable branches and would not know which targets to give up.
- **Baseline for the benchmark:** Brute force over a grid and random inputs, against ours.

## Problem

A guard (`when`) decides whether a step runs. The designer wants to know, before anything runs, whether two branches can both run, whether a case is handled by none, whether a guard can never be true, and which small set of inputs makes every guarded step run and be skipped. Each question is "is there an assignment of the variables that a guard reads for which this formula holds?".

## Why a library does not solve it

An SMT solver (Z3) answers all of this but is a binary of its own, and the engineering notes of the repository allow the standard library only. The guards are a small fragment (comparisons with constants, differences of two variables, membership, booleans, and, or, not), so a full solver is not needed; what is needed is a solver that is exact on that fragment and says "unknown" outside it instead of guessing. A test-generation library would have the same difficulty: it needs the join rules of the engine, which no library knows.

## What is borrowed (textbook algorithms, named)

- Difference constraints and Bellman-Ford: a system of `x - y <= c` is satisfiable iff its graph has no negative cycle, and the shortest distances from a source are a solution (Cormen et al., chapter on shortest paths).
- Disjunctive normal form: a formula is satisfiable iff one of its conjunctive clauses is.
- Interval sets for the constraints on one variable.
- Set cover: greedy (a ln n approximation) and branch and bound for the exact minimum.
- Kleene three-valued logic for a guard with an atom whose value is not known.

## What is ours (the transformation and the code we write)

- `solver/predicate.py`: the predicate tree (atoms `Cmp`, `Diff`, `Member`, `Truth`, `Opaque`), negation normal form, DNF with a cap of 64 clauses checked after every step so that a product that would be huge is never built, evaluation in three values.
- `solver/domains.py`: interval sets over exact rationals (`fractions.Fraction` from the text of the literal, never from a binary float); integers are tightened to closed integer pieces; finite and cofinite string sets; booleans.
- `solver/diffgraph.py`: Bellman-Ford with a virtual source, edge weights as pairs (constant, number of strict edges) compared lexicographically, and the witness from the distances with a concrete step for the strict edges.
- `solver/solve.py`: the three answers (`sat` with a witness, `unsat`, `unknown`), the per-clause solving, integer tightening of each edge when both variables are integers, mixed integer and real variables read over the reals with the witness checked, the cap on the pieces of the variables that meet in a difference (256), and a final check of every witness with the evaluator of the predicate.
- `solver/lower.py`: the lowering of an expression of the DSL to a predicate through a resolver that says which references are variables and with what domain; everything outside the fragment is one opaque atom.
- `analysis/variables.py`, `guards.py`: the resolver from the plan and the signatures of the actions; branch groups, overlap, gaps, dead steps.
- `analysis/generate.py`: the exact run condition of a step (its guard with the join rules of the steps it needs), the candidates, the cover. `analysis/predict.py`: the optimistic run with concrete values, used as the judge of what a candidate covers. `service/cases.py`: the mocked run through the simulation of the engine and the comparison.

## Adaptation: where the plain textbook version is wrong

- **Strict inequalities.** Plain Bellman-Ford with numbers as weights treats `x < y and y < x` (a cycle of weight zero) as satisfiable. Ours counts the strict edges in the weight, and a cycle of zero with a strict edge is negative. Tests: `test_a_zero_cycle_is_satisfiable_unless_an_edge_is_strict`, `test_strict_and_closed_ends`; with the strict edges treated as closed, 4 tests of the suite fail (checked by changing the code).
- **Integers have no value between neighbours.** A plain real solver says `x > 5 and x < 6` over integers is satisfiable. Ours tightens each strict atom over integers. Tests: `test_integers_have_no_value_between_neighbours`, `test_a_difference_between_integers_is_tightened`; without the tightening 2 tests fail (checked by changing the code).
- **Floating point.** A constant `0.1` as a binary float changes what is strict. Ours reads constants as exact rationals. Test: `test_exact_decimals`. The witness of a strict chain takes a concrete step computed from the distances; a fixed step instead made 4 tests fail (checked by changing the code).
- **A clause with an atom the solver does not understand.** A solver that treats an unknown atom as true reports a branch overlap that does not exist; one that treats it as false reports a dead step that is alive. Ours: the clause is `unsat` only if the rest is, and is never `sat`; the answer is `unknown`. Tests: `test_a_clause_with_an_opaque_atom_is_unsat_only_if_the_rest_is`, `test_overlap_with_an_opaque_guard_claims_nothing`.
- **The cap.** A DNF that is cut at the cap must not say `unsat`. Test: `test_too_many_clauses_is_unknown_not_unsat`.
- **Types.** At run time `true` is not `1` and `==` of different types is false. Ours reads `true` as a boolean and decides `==` of different types. Test: `test_a_type_mismatch_between_a_variable_and_a_constant` and the lowering compared with the evaluator of the engine on 2,500 random guards.
- **A guard alone is not the condition of a step.** A step behind a skipped step is skipped under `all_success`. A generator that solves the guard of the step only emits a case that does not run it. Ours solves the guard together with the join rules of its ancestors, and decides what a case covers by a separate prediction. Test: `test_a_step_behind_a_guarded_step_needs_its_ancestors_to_run`, `test_a_quorum_of_guarded_steps`.
- **Greedy cover is not minimal.** The greedy rule can pick a case that covers most targets and then need two more where two cases would have been enough (three cases where two do, found on a random workflow). Ours then searches for a smaller cover with branch and bound within a fixed budget. Test: `test_random_workflows_the_set_is_small`.

## Pseudocode

```text
check(pred, domains):                          # three answers
    clauses <- dnf(nnf(pred), cap = 64)        # None -> unknown
    for clause in clauses:
        result <- solve_clause(clause, domains)
        if result is sat and holds(pred, witness) is True: return result
    return unknown if any clause was unknown else unsat

solve_clause(clause, domains):
    one-variable atoms   -> restrict the interval / string / boolean set of the variable
    opaque atoms         -> if the rest is unsat: unsat; else unknown
    two-variable atoms   -> edges (x - y <= c, strict?) with weights (c, s), both orientations
                            integers: tighten the edge; every piece of the variables is a case
    bellman_ford(edges)  -> negative cycle (c < 0, or c = 0 and s > 0): unsat
                            else distances -> values for the variables, with a step for strict edges

generate(plan):
    run[s] <- guard(s) and join(s, run[needs(s)])         # exact condition
    for target (s, runs) in guarded steps x {run, skip}:
        r <- check(run[s] or not run[s], domains)
        unsat -> infeasible;  sat -> a base candidate
    candidates <- bases and, for each base, one-variable changes (enum values, constants and neighbours, bounds), at most 600
    reach[c] <- targets that predict(plan, c) decides as run or skip
    cover <- greedy(reach); better <- exact_search(reach, smaller than |cover|); take better if it exists
    missed <- feasible targets that no candidate reaches
```

## Complexity

The DNF has at most 64 clauses; for each clause the one-variable restrictions are linear in the atoms, and Bellman-Ford on the variables that meet in a difference is O(V E) with at most 256 combinations of pieces. `check` is therefore O(64 * 256 * V E) at worst and in practice a few atoms and well under a millisecond (benchmark A). The generator calls `check` twice per guarded step, builds at most 600 candidates, and predicts each in O(steps + edges); greedy cover is O(T C) with T targets and C candidates; the exact search is exponential in the worst case and stopped by a budget of nodes. Memory is O(candidates * targets).

## Oracle (independent check)

- The solver against brute force over a grid of bounded integers, enumerations and booleans on 500 random predicates (exact: `sat` iff a grid point satisfies), and on 250 over reals (never wrong, `unknown` allowed); `tests/unit/solver/test_solve.py`.
- Bellman-Ford against Floyd-Warshall (a second algorithm, written separately in `tests/support/floyd.py`) on 600 random systems, and a brute-force search on small integer systems; `tests/unit/solver/test_diffgraph.py`.
- Every witness of every answer is evaluated by the predicate before it is returned.
- The lowering of an expression against the evaluator of the engine on 2,500 random guards (two independent implementations of what a guard means); `tests/unit/solver/test_lower.py`.
- The prediction of a run against the engine itself on 480 random workflows with every join rule (`tests/unit/analysis/test_predict.py`): every step the prediction calls run or skipped ends so in a simulated run.
- The generator against a brute-force grid on the guards of random workflows (`test_generate.py`): every target is covered or proved infeasible, what a case claims is what `predict` says, and no assignment of a grid reaches a target that was proved infeasible. The mocked run compares the engine with the prediction for every case of the command `flowstat tests`.
- Five deliberate faults in the solver (no integer tightening, strict edges treated as closed, an opaque clause not checked for the rest, a fixed delta, `true` read as `1`) make 2, 4, 1, 4 and 4 tests fail.

## Measurement

`benchmarks/bench_solver.py`, `research/solver-measurement.md`. Against brute force over 10,000 assignments the solver is 55 to 70 times faster up to 8 atoms and never disagrees; at 32 atoms the cap of 64 clauses makes 64% of the random predicates `unknown`, and raising it to 4096 answers them but is only twice as fast as the grid. The generator covers all feasible targets of 294 random workflows with 2.04 cases on average, against 6.15 for one case per target; random inputs cover 68.7% with as many cases as ours and need 53 cases to reach what ours reaches.

## Stated limits

- The fragment is small: comparisons of a variable with a constant, differences of two numeric variables, membership in a list of constants, booleans, and, or, not. Calls, `* / %`, ordering of strings, comparisons with `null`, references to lists or records and sums of two variables are opaque; a guard that has one is never decided `sat`.
- Strings: no ordering and no pattern; text that must match a `pattern` is not generated, the caller gives it.
- The cap of 64 clauses and the cap of 256 combinations make the answer `unknown`, never a wrong one.
- A branch group is a heuristic (a set of guarded steps with the same `needs` and guards over the same variables); a group that is meant to be partial is silenced by writing the missing guard.
- A step that is dead because an ancestor is always skipped is found by the generator ("cannot happen") but is not reported as a warning at publish; that is the optimistic run of C2 (M5).
- The instances of a `foreach` step are not analysed; a guard that reads a step that did not run, or an opaque one, gives "no input found".
- Mocked outputs have the default of their declared type, apart from the variables that guards read; a contract that fails on such a value shows up as a difference.
