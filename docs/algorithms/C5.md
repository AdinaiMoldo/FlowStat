# C5. Version migration

Increment: I6, built in M8. Part 1 (conformance) is finished in US-32; part 2 (handover) is added in US-33.

## Two levels

- **Level 1 (known algorithm, our transformation):** Trace conformance: replay of a recorded history through the decision function of the new version; re-typing of completed outputs.
- **Level 2 (built on the output of level 1):** Ownership handover behind an epoch fence: the run moves to the new version only if level 1 accepts the trace.
- **Dependence:** Level 2 acts on the verdict of level 1; a handover without conformance could continue a run that the new version cannot explain.
- **Baseline for the benchmark:** Stop and restart, against ours: runs preserved and duplicate owners (must be zero) in the crash-during-handover suite.

## Problem

A statistician starts a run of version 3 of a workflow. While it waits for the chief statistician's approval, the designer publishes version 4 (a notification step, a longer retry on the publication). The run must be able to go on under version 4, but only if version 4 could have produced the history it already has: the steps that ran must be the same pieces of work, they must have been allowed to run by the join rules and guards of the new version, and what the steps still to come will read must exist in the outputs already recorded. If any of this fails the run must stay on version 3, and the person must be told every reason, not only the first.

## Why a library does not solve it

Workflow engines that allow a change of definition under a running instance (Temporal's patching, Camunda's process instance migration) either ask the programmer to keep the old code path forever or take a mapping of old activities to new ones written by hand, and check little else. Process mining has conformance checking (token replay, alignments) for a trace against a Petri net; it needs a net, a model of the workflow in another formalism, and it answers with a fitness number, not with reasons a designer can act on. The plan here is a plain graph with joins and guards, and the answer has to be a list of causes with a step and a code.

## What is borrowed (textbook algorithms, named)

- Trace replay (conformance checking, van der Aalst): the recorded trace is replayed on the new model, and a step that cannot be explained by the model is a deviation. We replay on the plan of the new version with its own decision function instead of a Petri net.
- Event sourcing: the state of every step after the history is a fold over the events, the same fold as `Scheduler.restore`.

## What is ours (the transformation and the code we write)

`migration/conformance.py` folds the history into the state of each step, then asks, for every step of the new plan that has events, whether the new plan makes the recorded decision from the recorded values: the join rule is the engine's own function (`join_verdict`, made public for this), the guard is evaluated by the engine's evaluator on the recorded inputs and outputs. `migration/retype.py` takes the steps that have not started and tries each of their reads on the recorded outputs (a missing field, a value of another type than the argument of the action). Every cause becomes a reason `E-MIG-001` to `E-MIG-008` (docs/api-spec.md, section 10). The pure function takes two plans, a history, the inputs and the signatures and returns a verdict; `service/migration.py` compiles both versions from their stored text and catalogue snapshot and lists the unfinished runs.

## Adaptation: where the plain textbook version is wrong

The plain replay, restoring the history under the new plan, trusts the recorded states and raises only for a step the new plan does not know. It accepts a changed action of a step that already ran, a guard that is now false for a step that ran, and a new predecessor that never ended; the run then goes on as a workflow that never produced its past. `test_restoring_the_history_under_the_new_plan_accepts_what_the_check_refuses` runs these three pairs through `restore` (no error) and through the check (refused). Three cases are specific to this plan language: a failed step keeps the `on_failure` it failed under (changing it would change the run retroactively, because the restore re-applies the stop), a step ended `UPSTREAM_FAILED` or `SKIPPED` must still be ended so by the new join rule or guard, and inputs are resolved again under the new version (a new default is added, a refused value is a reason).

## Pseudocode

```text
check(old, new, events, inputs):
    h = fold(events)                                   # state, started, touched, outputs
    if h.finished or h.undoing or an uncertain step: return NEVER_MIGRATE only
    inputs' = resolve(inputs, new)                     # E-MIG-008 for each refusal
    for each step with state RUNNING: E-MIG-002
    for each old step with events:
        absent from new                  -> E-MIG-003
        action/with/ensures/compensate/loop differ, or on_failure differs and it FAILED -> E-MIG-004
    for each new step with events:
        a predecessor (new needs) has not ended           -> E-MIG-005
        recorded fate vs join_verdict(new join, preds)    -> E-MIG-005 when they differ
        recorded fate vs new guard on the recorded values -> E-MIG-006 when they differ
    for each new step without events: E-MIG-007 for a read the outputs cannot serve
    kept, added, pending, dropped = set differences of the two plans and the touched steps
```

## Complexity

Linear in the number of events plus the size of the new plan, with one evaluation of each guard and each read: O(E + S·r), where S is the number of steps and r the references per step. The history is folded once.

## Oracle (independent check)

If the verdict is "migratable", the claim is that the new plan explains the history. `test_a_migratable_history_is_explained_by_the_new_plan` makes the claim testable: for seven pairs of versions and every cut of the history of a run (after every event, with and without a failing step), when the verdict is yes the history is restored under the new plan without error and, in a run of the new plan from the start given the recorded results, every step that has a fate in the history ends in that same fate. The oracle is the engine itself, run the other way (simulation), not the code of the check.

## Measurement

`benchmarks/bench_migration.py`: a check of the nine-region example takes about 0.12 ms (median) per history of up to 33 events, so a listing of a thousand unfinished runs costs about a tenth of a second plus compiling the two versions once. Conclusion in `docs/research/m8-measurement.md`.

## Stated limits

- Level 1 compares the plans as compiled; it does not try to prove that two different actions are equivalent, so a change of action of a step that ran is always refused.
- A guard is judged on the final recorded outputs, not on those at the moment of the decision; the compiler allows a guard to read only ancestors of its step, so the two agree.
- A step that was added with a join over steps that already ended may start as soon as the run is restored; the check does not ask whether a person wants that.
- Part 2 (handover) is added in US-33.
