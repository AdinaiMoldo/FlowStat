# M9. Hardening

Status: in progress (started 11 November 2026). Size: 50 SP (US-36 to US-43, DOC-7 to DOC-9).

## Goal

What the earlier milestones carried forward is built or dropped with a reason, and the project can be read as a report. A process that starts finds the runs it owns and goes on with them; the registry says whether a service answers; a designer can give an approval a time limit; an admin can limit the hosts that a workflow may call and replace the key of a deployment; the pages refresh themselves. The repository holds the diagrams the Proposal asks for, a traceability matrix with a row for every story and every non-functional requirement, the burndown and velocity charts made from the backlog, and a coverage gate that checks each of the C1 to C6 packages and not only the total.

## Readiness audit (11 November)

M9 was checked against the Project Proposal (sections 9 and 11: artefacts, NFR-01 to NFR-09, DR and UR), the Playbook (Definition of Done, section 9 on the report), the carry-over lines of `M2.md` to `M8.md`, `journal.md`, `traceability.md`, `negative-check.md`, `docs/diagrams/` and the measured coverage of every package. Fifteen findings. Each is closed in a story above or in the order of work below.

1. **There is not one diagram.** `docs/diagrams/` holds a README. The Playbook says a diagram is born with the code it describes, and the Proposal lists twenty. This is a miss of the process from M1 on, not a thing left for the end on purpose. Closed by DOC-8 and DOC-9, and the rule is kept in the order of work: the diagram of a function is drawn from the card and the code together, and a test compares the states of a state machine with the enumerations of `model/`.
2. **The traceability matrix lacks requirements.** It has rows for NFR-01, NFR-02 and NFR-09 only. NFR-03 (golden diagnostics), NFR-04 (soundness of availability), NFR-05 (one owner after a crash), NFR-06 (usability), NFR-07 (Windows and Linux), NFR-08 (a permission test per endpoint) and the rows UR-04 and UR-05 are missing, and US-30 to US-34 are keyed by function (`B5`, `C5`, `A5`) and not by the requirement they satisfy. The NFR-09 row still says "98% at the end of M2". Closed by DOC-7.
3. **The coverage gate is not the gate of NFR-09.** `fail_under = 90` is on the whole package. Measured today per package (line and branch): model 99.3%, dsl 99.2%, solver 96.6%, compiler 98.4%, analysis 92.0%, engine 98.7%, recovery 100%, migration 90.7%; together 96.2%. Every package passes, `migration` by 0.7 point. A script that checks each package, run in CI, closes the gap (DOC-7).
4. **`negative-check.md` has an empty table.** The criteria check of C1 to C6 was to be filled when each function was finished. Closed by DOC-7, from the cards.
5. **The documentation stories are not tracked.** The Proposal has DOC-1 to DOC-6 (3 SP each, the report section of an increment) and DOC-7 (5 SP). `backlog.md` has none. Decision: the review and the retrospective of each of `M1.md` to `M8.md` are the sections DOC-1 to DOC-6 asked for, and they are not counted again; DOC-7 is in M9 and the diagrams are DOC-8 and DOC-9, new, because they were never made. Recorded in `backlog.md` and `journal.md`.
6. **No burndown and no velocity chart exist**, and the data is only the dates in `backlog.md` (5, 8 and 9 November) and the sizes of the milestones. DOC-7 makes the charts from the backlog with a script, so they cannot disagree with it. The velocity is per milestone and the time axis is the milestone, not a date (the plan has no due dates).
7. **Resuming unfinished runs at start does not exist.** `flowstat resume` and the route resume a run on request; no process looks for its unfinished runs when it starts, and four milestones said "M8" and then "M9". The question M8 left open, which of several processes resumes which run, has an answer since M8: the table of ownership. A store resumes the runs it `OWNED` and nothing else, and one SQLite file has one process that writes (US-36).
8. **The status of a service in the registry is the one recorded at start and stop.** A machine restart leaves `running` for ever (US-37).
9. **The time limit of a waiting step** was in the edge cases of C3 and in no story, and moved from M2 to M3 to M9 three times. It needs the grammar (a field `timeout`), the checker (a limit on a step that cannot wait), the scheduler (a deadline), and the recovery (the deadline comes from the recorded time of the wait, never from the clock of the process). It is the one story of M9 that changes a C function, so it is first among the code stories, test before code (US-38).
10. **`http.call` may reach any host** (`dsl-spec.md` says "comes with the deployment (M8)"; it did not). US-39.
11. **The keys of a deployment cannot be replaced.** The control key sits in clear text in the core's registry (stated limit of M8) and none of the four keys can be rotated without redeploying. US-40.
12. **A report costs a compile.** 8 ms per report and 5.5 ms per listed run (`research/api-measurement.md`); the plan of a published version never changes (DR-03), so a cache keyed by workflow and version cannot go stale. US-41, measured before and after, kept only if it pays.
13. **The pages refresh only on a click.** US-42, polling while the tab is visible.
14. **NFR-06 is a test with a colleague and cannot be run by the author alone.** The Proposal asks for a valid five-step workflow in 30 minutes after a 15-minute introduction. This milestone prepares the exercise (the introduction text, the task, the record sheet) and the matrix says `not verified` until it is done; it does not invent a result.
15. **NFR-07 asks for the suite in a Linux container.** CI runs it on Ubuntu and on Windows; `scripts/test-in-linux.sh` runs it in Docker, and there is no Docker daemon in the development sandbox. The matrix says what was run: Windows and Ubuntu runners, not a container of the suite.

Stale sentences found while reading and corrected where they are met: `dsl-spec.md` (hosts of `http.call`), the carry-over line of `M7.md`.

## Retrospective

- Worked: measuring before deciding. The plan cache had its rule written before the numbers (kept only if a report is at least twice as fast) and the numbers decided. The matrix row for NFR-01 sent a long chain through the analyses of M5, which no benchmark had done, and found a defect (a draft of 500 guarded steps ended in an internal error); it became US-43 with its tests first, its card and its measurement.
- Worked: tests that compare a diagram with the code, both ways, each checked by putting a fault into the source. A diagram of this kind goes red when the code moves, so it does not drift the way the diagrams planned for M1 to M8 would have.
- Worked: the gate per package. The total was 96% and hid that `migration` was at 90.7%; the script reads each package and CI fails on the lowest.
- Went wrong: the diagrams and the matrix were left to the end of the project, which the Playbook says not to do. DOC-8 and DOC-9 cost 13 SP at the end for what would have been a small part of each increment.
- Went wrong: stacked branches and squash merges. After each squash the next branch conflicted in the same four documents (`backlog.md`, `journal.md`, `M9.md`, `traceability.md`), and resolving by taking both sides left a duplicate row in `main` (US-41 and US-42 as `not started` beside `done`), found by reading the table and removed in the branch of US-43. A pull request that conflicts with `main` gets no CI run at all, so the branch of US-43 showed no check until `main` was merged into it. One branch per story was kept; the cost is a merge of `main` after every squash.
- Went wrong, small: a test of the time of the analysis with a limit of 3 s passed locally and failed on both runners, which run under coverage. It now has a loose limit and says where the real figures are.
- Cost that should be said plainly: two requirements are not fully verified (NFR-06, NFR-07 in a container), and they are the two that need something the author does not have here, a colleague and a Docker daemon. The matrix says so and carries no invented result.
- Velocity: 50 SP planned and delivered; 3 SP of it (US-43) were not in the plan of the audit and came from the measurement. The 47 SP of the audit are done as planned.
- Next: the tag `m9` ("M9: Hardening") is to be created on `main` after this is merged, then the milestone and issues #80 to #89 and #96 are closed.
