# M4. Predicate solver

Status: done (5 November 2026). Size: 19 SP (US-20, US-23, US-24).

## Goal

The designer is told about guards before anything runs. Two branches that can both run, or that leave a case uncovered, are reported with a value that shows it; a step whose guard can never be true is named; and a minimal set of test inputs is generated that makes every guarded step run and be skipped where that is possible, run with mocked actions, with any difference between what the analysis predicted and what the engine did reported. All of this is done by a solver of our own (a difference graph with Bellman-Ford, no Z3), which answers `sat`, `unsat` or `unknown` and never claims more than it has proved.

## Readiness audit (5 November)

The milestone was checked against the Project Proposal (section on C6, the fragment, the stories) and against the code of M3 before the first line of code. Twelve gaps were found. Each is closed in `dsl-spec.md` (sections 3.2 and 8) or in the order of work below.

1. **Nothing says where the domain of a variable comes from.** US-20 speaks of "the decision enum", but the DSL declares no enums and the action `approval.wait` only says "the answer (`decision`, `by`)". Without a domain the solver cannot say that `escalated` is uncovered. Closed: a variable is a reference with a known domain. An input has its declared type; an output field has the type its action declares (the registry gives Python types, mapped to int, float, bool, string, list). The decision of `approval.wait` is an enum whose values are the optional argument `decisions` of the step (default `approved`, `rejected`). A reference with no known domain is opaque (3.2).
2. **The fragment of the Proposal does not match the grammar.** The Proposal has atoms `x in {c1, c2}`; the grammar has no list literal (open point since M1) and `x in y` takes a catalogue list, a string or a record. Closed: the grammar gets a list literal `[a, b]` as a primary, so `${approve.decision} in ['approved', 'escalated']` is expressible and is in the fragment. This closes the open point of M1; the parser, the evaluator, `to_source` and their golden tests change (absorbed in US-20).
3. **Which comparisons are in the fragment is not written down.** Closed (3.2): `ref op literal` and `literal op ref`; `ref ± literal` on either side; `ref - ref op literal`, `ref op ref ± literal`; `ref in [literals]`; a bare boolean reference and `not`; `and`, `or`, `not`. Everything else (a call such as `len` or `exists`, `*`, `/`, `%`, ordering of strings, a comparison with `null`, a reference to a list or a record) is an opaque atom.
4. **Three answers, not two.** A solver that says "no" when it does not know produces false warnings and false proofs. Closed: every question is answered `sat` (with a witness), `unsat` or `unknown`. A clause with an opaque atom is `unsat` only if the rest is, and otherwise `unknown`; a DNF that grows past the cap of 64 clauses is `unknown`. A warning is never based on `unknown`; the designer gets an information-level note instead (8).
5. **Comparisons of different types.** At run time `==` accepts any two values and `true` is not `1`; ordering of a string and a number is an error (3.1). Closed: `==` with a constant of another type than the declared type of the variable is false and `!=` true; an ordering of different types is opaque, because the run would fail and not branch.
6. **Numbers.** Integer and float variables, exact strict inequalities. Closed: all constants and weights are exact rationals (`fractions.Fraction`, from the text of the literal, never from a binary float); a strict atom over integers is tightened (`x < 6` is `x <= 5`), and a relation between an integer and a float variable is read over the reals. The weight of an edge of the difference graph is a pair (constant, number of strict edges); a cycle is negative when the constant is below zero or is zero with a strict edge.
7. **What is a "branch"?** The Proposal compares "the branches" without saying which steps. Closed (8.1): a branch group is a set of at least two steps with a `when`, the same `needs` and guards over the same set of variables, not instances of one `foreach`. Guards over different variables are independent choices, not alternatives, and are not compared. A single guarded step is an optional step and gets no coverage warning. This is a heuristic and is written down as a limit.
8. **A step can be dead for reasons the guard does not show.** US-23 says "contradicts the constraints on the inputs", but an input has no constraints beyond its type, a pattern and a catalogue list. Closed: an input may declare `values` (the allowed constants), `min` and `max`; they are checked when a run starts (E-INPUT-006 to 008) and the solver reads them as the domain. Dead because an ancestor is dead or skipped is the optimistic-run condition of C2 and comes in M5; M4 reports a guard that is unsatisfiable by itself (8.2).
9. **Warnings do not exist in the pipeline yet.** `flowstat publish` treats any diagnostic as an error and `SaveResult.diagnostics` is "empty when the draft is ready". Closed: warnings and notes come from the analysis, not from the compiler; publish is blocked by errors only and prints warnings; the layer rule (analysis above compiler) is kept by the service calling the analysis after a successful compilation.
10. **The generator needs more than inputs.** A guard reads action outputs (`approve.decision`), so a test case is the inputs plus the outputs the mocked actions return. Inputs that no guard reads (here `quarter`, with a pattern) cannot be invented, since the solver has no regular-expression generator and must not use a library. Closed (8.3): the case varies only the variables that guards read; the other inputs are given by the caller (`--input`); an output field no guard reads gets the default of its type (0, 0.0, false, "", an empty list), and a contract that fails with a mocked output is reported as a difference, not hidden.
11. **"Executed" depends on the ancestors.** A target "step s executes" is not the truth of its guard: an ancestor that is skipped skips `s` under `all_success`. The exact condition is the optimistic-run condition of C2 (M5). Closed: the generator takes the conjunction of the guard with the guards of its ancestors as the candidate to solve, then decides what a case really covers by a prediction that applies the four join rules to concrete values (`analysis/predict.py`), and the engine's own run is compared with it. A target that no candidate covers is reported as "proved infeasible" (the guard alone, or its negation, is unsatisfiable) or "no input found" (nothing is claimed).
12. **The reference interpreter is not needed to start and is a risk to scope.** The backlog lists it in M4; the Proposal needs it as the oracle of C2 (M5). Closed: M4 checks the solver against brute force on a grid and the lowering of expressions against the evaluator of the engine (two independent implementations of the meaning of a guard); the reference interpreter of whole workflows moves to M5 where C2 needs it (the backlog is corrected).

Two points are left out on purpose: the validation of an approval answer against `decisions` at run time (it belongs to the REST API of M6, where an answer arrives from outside), and regular-expression generation for string inputs with a `pattern` (not in the fragment; the caller gives such inputs).

## Review

Delivered against the goal: the designer is told about guards before anything runs. `flowstat publish` prints a warning for two branches that can both run (with a value that shows it), for a case that no branch handles (the example with `escalated` names it), and for a step whose guard can never be true; the example itself gives no finding. `flowstat tests` generates a small set of inputs that make every guarded step run and be skipped where that is possible, says which targets cannot happen and which it could not reach, runs the cases with mocked actions and reports every difference between the prediction and the engine (on the example: 2 cases cover 4 of 4 targets, prediction and engine agree). All three stories pass their acceptance criteria (`tests/acceptance/`). The solver is our own code (no Z3, no sympy): difference graph, Bellman-Ford with strict edges, a DNF with a cap, three answers.

## Retrospective

- Worked: the audit once more. Twelve gaps on paper, among them that the DSL had no domain for a variable, no list literal, no warnings in the pipeline, and that "step runs" is not the truth of its guard. Closing them first made the three stories small; none of them needed a change of the design afterwards.
- Worked: three independent judges of one meaning. The solver, the prediction of a run and the engine itself check one another (the lowering against the evaluator, the prediction against the simulation, the generator against a grid), and each disagreement found so far was in my test and not in the code, which is the cheaper way for it to go.
- Worked: breaking the solver on purpose. Five deliberate faults each failed the suite, so the brute-force comparison is a check and not a ritual.
- Went wrong: three wrong expectations in the tests of US-20 (two decisions make `!= 'rejected'` the same guard as `== 'approved'`, so there are two findings; a boolean guard `flag` with `flag == true` leaves false uncovered; the unsatisfiable guard next to a branch gives a second finding). Each time the analysis was right and my sentence in the test was the guess. Same remedy as in M2 and M3: derive the expected value from the specification.
- Went wrong: the greedy set cover was not minimal (three cases where two do). The test of smallness would not have caught it; a comparison with an exact search did. The exact search was added after the greedy pass.
- Went wrong: the local lint accepted an import order that CI refused. The local ruff and the CI one are not the same version. Next: run the CI command from a fresh install before the push when the tool is new.
- Cost that should be said plainly: a guard with an atom outside the fragment (a call, `*`, a string ordering) is never decided, so its targets end as "no input found" and a group that contains it is "not analysed". The fragment covers the guards of the example and of the usual workflows, but a designer who writes `len(...)` gets a note and no proof.
- Velocity: 19 SP planned and delivered. The extra work not in the plan was the shared lowering of guards (`analysis/variables.py`), the exact search for the cover and the wording of the cases; the reference interpreter of whole workflows (planned in the backlog for M4) moved to M5.
- Next: M5 (analysis: types, C2, feasible critical path) starts with its readiness audit. The tag `m4` is to be created on `main` after this review is merged.
