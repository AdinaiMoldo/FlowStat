# M8. Evolution

Status: in progress (started 9 November 2026). Size: 24 SP (US-32, US-33, US-34).

## Goal

A designer publishes version 4 of a workflow while runs of version 3 are in flight, and is told for
each run whether it can continue under version 4 and, when it cannot, why. An operator moves a run
that can to version 4: the service of version 4 then owns it, every command sent to the old owner
is refused, and a crash at any point of the move leaves exactly one owner and no lost run. An admin
sees the failure rate and the average duration of every workflow. This is C5 (conformance first,
handover second, as `journal.md` decided) and A5.

## Stories

| Story | Function | SP | Given / When / Then |
| --- | --- | --- | --- |
| US-32 which runs can move | C5 | 13 | Given a run of v3 waiting at approval and v4 adds a step after approval, then the run is migratable. Given v4 changes a completed step, then it is not, with the reason. Given v4 adds a region, then its instances are shown as pending |
| US-33 move a run | C5 | 8 | Given a migratable run, when I confirm, then the service of v4 owns it and every command to the old owner is rejected. Given a crash during the handover, then after restart exactly one owner remains |
| US-34 statistics | A5 | 3 | Given 10 runs with 2 failures, when I open statistics, then the failure rate shows 20% |

## Readiness audit (9 November)

The milestone was checked against the Project Proposal (C5, A5, DR-01, NFR-05, the UML of C5), the card
`algorithms/C5.md` (empty), `architecture.md`, `api-spec.md`, and the code of M3, M6 and M7 (`engine/scheduler.py`,
`compiler/plan.py`, `service/runs.py`, `service/driving.py`, `repo/runs.py`, `repo/deployments.py`, the shipper)
before the first line of code. Eighteen gaps were found. Each is closed in `api-spec.md` (section 10) or in
the order of work below.

**The verdict (US-32)**

1. **There is no plan stored for a run, only a version number.** A run knows `(workflow, version)`; its plan is compiled again on demand. Closed: the check takes two plans, both compiled from the stored versions with the catalogue snapshot each one froze (a region added to the catalogue exists only in the later snapshot), and a run's events. Nothing about the run is changed to make this possible.
2. **"Replay through the scheduler of the new version" must not run actions.** The scheduler is a pure state machine (events in, commands out), so the replay is that machine fed with recorded events and no driver. But `Scheduler.restore` takes the recorded states as truth and raises on an unknown step, which is the very thing the check has to report rather than crash on. Closed: `migration/conformance.py` has its own replay state over the new plan, with the same join rule (`engine.scheduler._join_verdict`, made public as `join_verdict`) and the same evaluator for guards (`engine.evaluator`); `restore` is used afterwards, for the owner that takes the run, when the verdict is yes. The two cannot drift because a test (the oracle) runs both.
3. **What is "touched", and what is "changed"?** A step is touched when the history has an event for it. It is changed when its action, its `with`, its `ensures`, its `compensate` or its loop binding differ between the two plans, compared as compiled values (not as text, so a comment or a reordering of keys changes nothing). A change of `retry` or of `on_failure` on a step that has already finished is allowed (the policy only matters while it runs); on a step that is running or waiting it is reported, since the new policy would apply from the next event. A change of the `needs` or the join of a touched step is not a text comparison either: it is judged by whether the recorded history is still an execution of the new graph (reason 4).
4. **Reasons are a closed list, all of them reported.** `NEVER_MIGRATE` (the run is compensating or uncertain: C4 owns it), `RUNNING_STEP` (a call is in flight; try again when it has finished), `REMOVED_TOUCHED_STEP`, `CHANGED_TOUCHED_STEP`, `UPSTREAM_CHANGED` (a started step could not have started under the new join rule), `GUARD_CONTRADICTS_HISTORY` (a skipped step whose new guard is true on the recorded values, or a started step whose new guard is false), `OUTPUT_INCOMPATIBLE`. The answer lists every reason, not the first, with the step and a sentence for each. The codes are `E-MIG-001` to `E-MIG-007` in the order above.
5. **A guard is judged on the recorded values, not on the inputs alone.** The evaluator needs the outputs of earlier steps; the replay keeps them as it goes (`SUCCEEDED` events carry the output), so the guard of a step is evaluated on exactly the context it had. A guard that cannot be evaluated on the record (a field the new text reads and the old output lacks) is `OUTPUT_INCOMPATIBLE`, not a crash.
6. **Re-typing (the card says "reuses the compiler").** The types of an action's outputs are declared once, in the registry, and do not depend on the version, so the static check of the new text already passed. What can still be wrong is the recorded value: a field a new consumer reads that the output does not have, or a value of another type than the argument the new consumer gives it to expects. `migration/retype.py` walks the `with` of the new plan, finds each argument that is exactly one reference to a recorded output, resolves the path in the record and tests `assignable(plain_type(value), declared type)` (the same functions as `analysis/types.py`). Stated limit: an argument that mixes text and references is not typed, as in the checker.
7. **Renamed steps.** The DSL has no `renamed_from`. A renamed step is a removed one plus a new one; if the old one was touched, the run is not migratable (`REMOVED_TOUCHED_STEP`). Stated, not hidden; adding the key is a change of the language and is not in M8.
8. **A region added to the catalogue.** The new instances exist in the new plan and not in the history, so they start `PENDING`; an instance with no predecessor (a late root) becomes ready as soon as the new owner takes the run. The answer lists them as `pending`, with the steps that were already there as `kept` and the removed untouched steps as `dropped`. A region removed whose instances were all untouched is `dropped` too; a region removed after its instance started is `REMOVED_TOUCHED_STEP`.
9. **Which runs are asked about.** The runs of version `n` of the workflow that have not finished (no `RUN_FINISHED`), in the core and in the services, from the copy the core holds. The answer says each run's owner. A run that finished is not listed (nothing to move); a run that is `FAILED` or compensating is listed with its reason, since the designer may wonder about it.

**The handover (US-33)**

10. **A run changes owner by changing where its log lives, and the log key is (run, seq).** The design of the Proposal appends `MIGRATING`, `MIGRATED_OUT` and `MIGRATED_IN` events. That cannot work with the outbox of M7: the old owner would write `MIGRATED_OUT` as event `k+1` of its log and the new owner `MIGRATED_IN` as event `k+1` of its log, and the core, which stores one copy by the pair (run, seq), would see two different events with one key and refuse the batch. Closed: **the fence is a table, not events.** Every store that can own a run (the core, each service) has `ownership(run_id, epoch, state, peer)` with the states `OWNED`, `MIGRATING`, `MIGRATED_OUT` (the state machine of the Proposal, with `MIGRATED_IN` as `OWNED` at a higher epoch). The log gets exactly one new event, `RUN_MIGRATED`, written by the *new* owner as the first event after the history it imported (`attempt` = the epoch, `message` = the old owner), so the history reads "moved here at epoch 2" and the numbers continue where the old log stopped.
11. **The protocol is three steps and recovery rolls forward.** (1) *Fence at the old owner*: one transaction, compare-and-set `OWNED(e)` to `MIGRATING(e+1, target)`; from then on every command for the run is refused and no driver advances it. (2) *Import at the new owner*: the run's row, its events and `OWNED(e+1)` in one transaction, idempotent by (run, epoch), then the event `RUN_MIGRATED`; the new owner restores the run with the new plan. (3) *Release at the old owner*: `MIGRATING` to `MIGRATED_OUT`. A crash between any two of these is repaired by `recover(run)`, which reads the ownership of both sides: the old one `OWNED` means nothing happened; `MIGRATING` and no import means repeat the import; `MIGRATING` and an import means release. It always goes forward, never back: the check was made before the fence and the history is frozen by it, so the import cannot be refused for a reason that appeared later. The pair of states `old = MIGRATING` and `new = OWNED` is the only moment two stores hold the run, and the old one refuses every command (it is fenced), so exactly one of them can act.
12. **Quiescence.** The fence is taken only when the run has no `RUNNING`, `COMPENSATING` or `UNCERTAIN` step (reason `RUNNING_STEP`) and the run is not being driven (the lock of M6). A run waiting at an approval is the case that matters, and it is quiescent. The cost is stated: a run in the middle of a long action cannot be moved until it finishes.
13. **A command that arrives during or after the move.** Decisions (`POST /runs/{id}/decisions`), resume and the start of a driver all go through one check of the ownership table; a fenced or released run answers 409 `E-API-003` with the new owner in the message (`E-MIG-010`). An approval that arrives while the run is `MIGRATING` is refused, not queued (the Proposal says queued; refusing is simpler and safe, and the person answers again at the new owner; stated).
14. **Who may move a run, and how does the core call a service?** A new permission `runs:migrate` for admin and operator (the roles that answer approvals). To call a service the core needs a credential it can send, which the other keys are not (the core keeps only their hashes). Closed: a fourth key per deployment, the *control key*, made with the others; the service stores its hash (`control_key_sha256` in the manifest, a user `control` of role admin in the service's own database) and the core keeps the key itself in the registry row, because it must present it. This is a secret at rest in the core's database, like the database file itself; stated as a limit, with the rotation of keys that is not done (M9).
15. **The new owner must exist.** The target is a deployment of the new version that is `running`, or the core itself (the core can own a run of any published version; this is how a run moves from a service back, and how a run of the core moves to a newer version of the core). The check is made before the fence; a target that is stopped or of another version than the one asked for is 409.
16. **The core's copy of a run follows its owner.** `runs.origin` (M7) becomes the owner: at release the core sets it to the new owner in the same transaction that records `MIGRATED_OUT` for a run it owned or for a run it only copied. The old owner's outbox then gets 409 for the run and leaves it out (already the rule of M7); the new owner's events continue the numbers. A test follows one run through core, service, service and reads the same history from the core at the end.
17. **The crash test is the proof.** The handover is run with a crash injected before and after every call of the protocol, on either side (the two stores are in-memory databases with a wrapper that raises on the n-th call). After `recover`, for every point: exactly one store is `OWNED` for the run at the highest epoch, the other is `MIGRATED_OUT` or never had it, no event is lost or doubled, and the migrated run finishes with the same report as the same run without a move. The baseline of the card, stop and restart, aborts the run and starts it again under the new version: it preserves 0 runs, and the number is written next to ours in the measurement note (`bench_migration.py`).

**Statistics (US-34) and the rest**

18. **What is a failure, and what is a duration?** Rejection is data (DR-02): a run that ends `GOAL_NOT_REACHED` did not fail. A *failure* is an outcome of `FAILED`, `COMPENSATED` or `COMPENSATION_FAILED` (a step failed under a policy that stops the run). The *rate* is failures over finished runs, so 10 finished runs with 2 failures give 20%; the statistics also give the number not reached, the number running, and the average duration of finished runs (`RUN_FINISHED.at` minus `RUN_STARTED.at`, the engine's own clock, so a run of the core and a run of a service are measured the same way). They are read from the stored events of the core, including the copy of the services' runs, and may lag (architecture.md). Permission `statistics:read`, admin only (the Proposal says "admin"). The average duration per *step* is not asked for and is not built; the scheduler's `durations` argument keeps its default of 1.

Triaged out of M8 and carried to M9 (hardening), with the reason: resuming unfinished runs at start (not in any story; it needs a decision about which of several processes resumes which run), the health probe of services (the status in the registry is the one recorded at start and stop), the plan cache (8 ms per report is not a problem at this size), key rotation, a live refresh of the pages. What M8 does take from that list is what the handover needs: `recover` for a move that a crash interrupted runs when the core starts and on demand (`POST /runs/{id}/migrate` with no body target repeats it).

Left out on purpose: migrating several runs at once (one confirmation per run; the page offers a button per row), a dry-run diff of two versions as text, an undo of a move (a run can be moved again by the same procedure to the version it came from if that version still conforms), moving a run between two cores.
