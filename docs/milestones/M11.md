# M11. Reporting campaigns

Status: planned (readiness audit written 18 November 2026). Size: about 84 SP, an estimate; each
story is re-sized when it starts.

## Goal

A quarter of reporting is an object of the system, and what happens to it can be followed: the
regions send forms, every form is checked against rules of its template, an error becomes a
problem that somebody corrects, a corrected form is a new version and the old one stays, the
consolidation says which regions it holds and is marked preliminary until the policy of
completeness is met, and the chief statistician approves one version of one result.

The value to say in one sentence: *FlowStat turns the regional reports into a checked, managed and
reproducible preparation of consolidated results.*

## Safe way of working

- `main` at the end of M10 is kept as the branch `demo-m10` (and the tag `m10` in the clone); it is
  the version to show if a later change is not ready.
- One branch per story, the story ID in the commit message, CI green on Ubuntu and Windows before
  the merge. A story is merged only with its tests and its documentation.
- The command `python scripts/exercise_setup.py start --logins --no-forms --with-history` keeps
  working after every story (a test starts it). New data for the demonstration is added behind new
  options, not by changing what the old command makes.
- The existing example `examples/quarterly_consolidation.yaml`, the API routes and the golden
  OpenAPI file change only by adding; a change that is not an addition is written in the journal
  with its reason.

## Decisions taken at the audit

1. **Where the rules live.** The rules of a template and the evaluation of a form are a pure module
   in the `model` layer, with exact numbers (`decimal.Decimal`). The page Forms and the workflow
   step `statguard.validate` both call it, so the check has one definition (the lesson of US-49:
   two definitions drift).
2. **Form files.** The path that `xlsx.read` reads (`<region>/<quarter>.xlsx`) stays and holds the
   current version, so the existing example and the API keep working. Each upload is also kept as
   a version, with its check result, in a table and an archive folder; nothing is overwritten.
3. **Tables are added, none is changed.** `campaigns`, `submissions`, `issues`, `consolidations`
   and `audit_events` are new tables made as the others are (`CREATE TABLE IF NOT EXISTS`).
4. **One source of truth for history.** The events of a run stay in `run_events`; the audit trail
   records what happens outside a run (uploads, settings, approvals of a result) and refers to the
   run by its identifier where there is one. It does not copy the events of a run.
5. **Final consolidation by a policy.** The policy of completeness is a setting of the campaign
   (default 9 of 9 valid forms); a preliminary result is allowed from a lower threshold and is
   marked as incomplete in the data, not only on the page. The old example keeps its 7 of 9 and
   is the preliminary case.
6. **No exactly-once claim.** The guarantees are those that exist: a repeated upload with the same
   content is recognised, a repeated approval of the same result version is refused, a batch is
   replaced and not doubled.

## Risks

- The form model is `code, name, value`. Rules of arithmetic need named indicators, so the
  template says which codes exist; the sample forms have five indicators and the rules are written
  for them. A real template of the Committee is not known to this project.
- The golden OpenAPI file and the API specification change with each story; each change must be an
  addition.
- A larger consolidation touches the engine (C3) and the recovery (C4); their tests (every cut of a
  history) are extended before the code, as the rules of the repository say.
- The page grows: Campaigns, Issues, Consolidations, Review and Audit are new views. An existing
  view that does the same task is extended instead of a new one made.
- The size is an estimate; Phase A is the part that must be finished, B and C are cut first if time
  runs short.
