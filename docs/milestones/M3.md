# M3. Fault tolerance

Status: done (5 November 2026). Size: 28 SP (US-13 to US-17).

## Goal

A run survives what goes wrong. A transient error is retried with growing delays, a failed run is undone in the right order, an engine that is killed at any point is restarted and finishes the run without repeating a completed step and without silently repeating an effect, steps whose outcome is unknown are left to a person, and all of this is tested against an action server that drops, duplicates and delays its responses.

## Stories

| Story | Function | SP | Given / When / Then |
| --- | --- | --- | --- |
| US-13 retries | C4 | 2 | Given retry: {max: 3} and an action failing twice, when I run, then the step succeeds on the third attempt with growing delays |
| US-14 compensation order | C4 | 8 | Given a, then b succeeded, both with compensate, and c failed under the compensate policy, then compensation of b finishes before compensation of a starts and the run is COMPENSATED |
| US-15 survives a crash | C4 | 8 | Given the engine is killed while idempotent b is RUNNING, when it restarts, then a is not re-run, b runs once more with the same idempotency key, and the run completes |
| US-16 uncertain steps | C4 | 5 | Given the engine is killed while a non-idempotent step is RUNNING, when it restarts, then the step is UNCERTAIN and nothing is re-run automatically; I can mark it done or retry it |
| US-17 misbehaving action server | C4 | 5 | Given the server executes a request and drops the response, when the engine retries with the same key, then the effect exists exactly once |

## Readiness audit (5 November)

The milestone was checked against the Project Proposal (section on C4, the lifecycles and NFR-02) and against the code of M2 before the first line of code. Eleven gaps were found. Each is closed in `dsl-spec.md` (sections 5.3 to 5.5) or in the order of work below.

1. **Events are stored after the run.** `RunService.execute` appends the events when the run is over, so a crash loses the history. The write-ahead rule needs the events to be committed before the commands that follow them are executed. Closed: the drivers store the new events after every scheduler call and before dispatching (section 5.5); `synchronous=FULL` is set on the database.
2. **No definition of "transient".** A retry of a permanent error only wastes time and repeats a side effect. Closed: the action reports a failure as transient or permanent; the workflow does not decide it (5.3).
3. **`retry` has no delay.** The DSL has `max` and `backoff` but no base delay, and "growing delays" (US-13) needs one. Closed: optional `delay` in seconds, default 1; no jitter, so a run is reproducible (5.3).
4. **A delay needs a clock and a sleep.** The scheduler must stay pure and the engine must not read the clock. Closed: a retry is a command `Start` with an attempt number and a delay; the driver waits (the thread driver with an injected `sleep`, the simulation on virtual time).
5. **`ensures` failing: retry or not?** Open point of M1. Closed: never retried (5.3).
6. **The compensation policy does not exist in the DSL.** `on_failure` accepts `fail` and `continue`; US-14 says "under the compensate policy". Closed: the value `compensate` is added (5.4); the shape validator and the plan change with US-14.
7. **The order and the arguments of a compensation were not defined.** Closed: a step is undone after all its descendants that are also undone, through steps without `compensate` too; arguments are those of the original call; failure handling and the outcomes COMPENSATED and COMPENSATION_FAILED are defined (5.4).
8. **The lifecycle has ten states, the Proposal text uses an eleventh.** UNCERTAIN appears in C4 and US-16 but not in the list. Closed: the step states are extended with UNCERTAIN, COMPENSATING, COMPENSATED and COMPENSATION_FAILED; UNCERTAIN is not terminal, and the run outcomes with COMPENSATED and COMPENSATION_FAILED.
9. **Actions do not declare idempotency.** The Proposal's action interface has an idempotency flag; `ActionSpec` does not. Closed: the flag is added, and the idempotency key reaches the action in its context; `email.send` is declared non-idempotent so that the UNCERTAIN path has a real case (5.5).
10. **Recovery needs to rebuild a scheduler from events.** The scheduler only produces events. Closed: `Scheduler.restore(events)` folds the recorded states and outputs (it does not replay decisions) and recomputes the counters; the rules for a step that was RUNNING are in `recovery/` (5.5). Resuming a run that was only waiting for an approval is the same mechanism, so the command line gets `resume`, and `resolve` for UNCERTAIN steps.
11. **US-17 needs an HTTP action and a fault-injecting server.** `httpx` is not installed and a third-party client adds nothing here. Closed: the action `http.call` uses the standard library (`urllib`), sends the key in the `Idempotency-Key` header and classifies answers; the server is a test tool (`tests/support/`) built on `http.server`.

Two points of the Proposal are left out on purpose:

- **A timeout for a waiting step** is in the C3 edge cases but in no story of M3, so no acceptance criterion exists for it. It moves to M9 (hardening) and is written down there; M2 said M3, and the review of M2 is corrected.
- **A warning for a step with side effects and no `compensate`** needs information about actions inside the compiler. It comes with the static analysis (M5).

A torn tail of the log cannot happen at the level of one event, because every append is a SQLite transaction; a gap or a different event with a used number is refused by the store (A2, M2).

## Order of work

1. This audit, the semantics in `dsl-spec.md` 5.3 to 5.5, journal entry.
2. US-13: states, events, `delay` in the DSL, retry in the scheduler and both drivers, the transient flag of an action error. Tests first.
3. US-14: `on_failure: compensate`, the saga planner and the compensation phase (`recovery/`), outcomes COMPENSATED and COMPENSATION_FAILED. Tests first, with an oracle for the order.
4. US-15 and US-16: write-ahead in the drivers, `Scheduler.restore`, recovery rules, UNCERTAIN, `resume` and `resolve`. Crash-injection suite after every event of the nine-region example (NFR-02), written before the recovery code.
5. US-17: the action `http.call`, the fault-injecting server, the exactly-once tests.
6. Measurement: restart from scratch and naive reverse order against ours, in the crash-at-every-event suite; algorithm card `algorithms/C4.md`.
7. Review, retrospective, tag `m3`.

## Review

Delivered against the goal: a run survives what goes wrong. A transient error is retried with fixed or exponential delays; a failed run under `on_failure: compensate` is undone in dependency order, in parallel within the limit; an engine that is killed after any event is restarted with `flowstat resume` and finishes the run without repeating a finished step; a step that was running and is not idempotent becomes UNCERTAIN and a person decides with `flowstat resolve`; a call whose answer was lost is retried and the effect exists once when the receiver honours the key. All five stories pass their acceptance criteria (`tests/acceptance/`).

| --- | --- | --- | --- |
| US-13 retries | C4 | 2 | `tests/unit/engine/test_retry.py` (every combination of `max`, backoff and failures), `tests/acceptance/test_us13.py` |
| US-14 compensation order | C4 | 8 | `tests/unit/recovery/test_saga.py` (naive oracle), `tests/unit/engine/test_compensation.py` (40 random sagas), `tests/acceptance/test_us14.py` |

Measurements: 993 tests (756 unit, 182 crash and fault injection, 52 acceptance), 98% coverage (gate 90%), CI green on Linux and Windows for every story. The crash suite cuts the history after every event of the nine-region example, of sagas with parallel undos and with a failing undo, and of random sagas, and compares the restored run with the uninterrupted one; three deliberate faults in the restore and two in the other parts (the idempotent flag of `email.send`, the planner of the order) each make it fail. Against the baselines (`research/recovery-measurement.md`): 2.6 repeated calls per crash point against 12 for a restart from scratch; no possible duplicate effect against 898 for plain replay on the random workloads, at the price of asking a person 898 times over 2,040 crash points; the order of compensation is exact and 2.6 times faster than reverse plan order. Algorithm card `algorithms/C4.md` is filled.

Changes against the plan, all decided during the work:

- The readiness audit found eleven gaps before any code; they are closed in `dsl-spec.md` 5.3 to 5.5. One more came up in US-17 and is below.
- The key of an attempt changes with every retry, so a retry after a lost answer would have been a new operation for the receiver. `http.call` sends the key of the operation (without the attempt number); `dsl-spec.md` 5.3.
- The rebuilding of a run is `Scheduler.restore` in the engine and not a function in `recovery/`: it needs the private state of the scheduler, and the engine layer cannot import the recovery layer. `recovery/` holds the write-ahead log and the saga order.
- UNCERTAIN releases its slot; a retry ordered by a person starts at once and can exceed the limit of parallel steps by one call.
- Default for an action is "not idempotent"; six of the seven registered actions say they are, `email.send` does not.
- New codes and events: E-REC-001, E-COMP-001, E-ACT-008 and 010; RUN_RESUMED, STEP_UNCERTAIN, STEP_RESOLVED; a column `decision` in the history table (old database files get it).
- New commands: `flowstat resume` and `flowstat resolve`; `flowstat run` now stores the history while the run goes on.

Not done in M3 and moved: a process that finds and resumes every unfinished run at start-up (M8, with the deployment and the switch of owner, C5); a list of hosts that `http.call` may reach (M8); group commit of events (not needed at the measured cost); a timeout for a waiting step (M9); a warning for a step with side effects and no `compensate` (M5).

## Retrospective

- Worked: the readiness audit again. Eleven gaps found on paper before the first line, among them that UNCERTAIN was missing from the list of states, that a compensation needs the arguments the step had, and that the history was stored only after the run. All but one are closed as the audit said; the rules for a running step ended up in the scheduler and not in `recovery/` (see the review), and the key problem of US-17 was not in the audit.
- Worked: writing the crash suite before the recovery and then breaking the recovery on purpose. The suite passed on the first run, which is a reason for doubt and not for relief; five deliberate faults (the attempt number of a repeated call, no repeated call, no completion of a partial stop, `email.send` marked idempotent, a planner that looks at direct dependencies only) each made it fail, so it is a real check.
- Worked: one scheduler core, driven by the simulated clock in tests and by threads in production. The restore, the compensation and the retries were all tested without a thread or a sleep, and the crash suite runs 170 crashes in two seconds.
- Went wrong: the audit did not catch the contradiction between the key of an attempt and "retries with the same key" in the story of US-17. It showed when the first exactly-once test was written. Next time: write the end-to-end test of the story's criterion at the audit, with the receiver, before the interface is fixed.
- Went wrong: a property test of the compensation first asserted equal final states for 1, 3 and 100 workers. It is false: with more workers more steps have succeeded when a failure stops the run. The assertion came from what I hoped, not from the specification; the specification now says it and the test checks what holds.
- Went wrong: smaller wrong expectations in tests (a whole-value `${...}` keeps its type, `ensures` needs `${...}` references). Same remedy as in M2: write the expected value from the specification.
- Cost of the design that should be said plainly: a run with many non-idempotent steps asks a person often (0.44 questions per crash point in the random workloads). The rule is right, the default is the safe one, and the remedy is an action that honours a key; but it will be felt if a workflow is full of mails.
- Velocity: 28 SP planned and delivered; the extra work not in the plan (the `decision` column, the operation key, `resume` with `--decision` for an approval that arrives later, the two benchmarks) was small.
- Next: M4 (C6: the solver and the test generator) starts with the same readiness audit against the Proposal and the tests first (C6 is a category C function: tests before code). The tag `m3` is to be created on `main` after this review is merged.
