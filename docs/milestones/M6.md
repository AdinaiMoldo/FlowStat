# M6. API, roles and deployment

Status: done (8 November 2026), tag `m6` to be created after merge. Size: 21 SP (US-25, US-29, US-30).

## Goal

A person or a program outside the process can use FlowStat over HTTP, and an administrator can turn a
published version into a service of its own. Over REST an external system starts a run and gets its id, or gets 422 with one error per
invalid input; an operator who tries to publish gets 403; an approval can be answered only with a
decision the step declares and only by someone who holds the title it names. An admin deploys
version 4 as a process (or a container) that answers on its own endpoint, with its own write-ahead log, and
returns the same results as the core's executor for the same inputs. The contract is in
`api-spec.md`; the OpenAPI file is a golden file.

## Stories

| Story | Function | SP | Given / When / Then |
| --- | --- | --- | --- |
| US-25 start a run over REST | B4 | 5 | Given a published workflow, when I POST valid inputs, then I receive a run id. Invalid inputs return 422 with field errors |
| US-29 restrict publishing | A3 | 3 | Given a user with the operator role, when they publish, then the API returns 403 |
| US-30 deploy as a service | B5 | 13 | Given v4 is published, when I deploy it, then the service answers on its endpoint and returns the same results as the core's executor for the same inputs |

## Readiness audit (8 November)

The milestone was checked against the Project Proposal (B4, B5, A3, A6, NFR-07, NFR-08, DR-04), against
the code of M5 and against the tools of this environment before the first line of code. Nineteen gaps
were found. Each is closed in `api-spec.md` or in the order of work below.

1. **The API stack is not installed where the tests run.** CI and `scripts/test-in-linux.*` install `.[dev]`, which has none of FastAPI, uvicorn, Pydantic, Jinja2 or the Docker SDK, and the test client of FastAPI needs `httpx`, which is in no extra that CI installs. Closed: the `dev` extra gains the test-only `httpx`; CI and both scripts install `.[dev,api,deploy]`. `docs/reuse.md` said `http.call` uses httpx; the action uses `urllib` (its own header says so), so the row is corrected: httpx is a test dependency.
2. **Two packages on layer 8 may not import each other, but the service must serve the same run routes as the core.** If `deploy` held the service app, it would have to import `api`. Closed: both apps are in `api` (`flowstat.api.service` is the service); `deploy` only builds bundles and starts them by module name. The routes for runs are one function used by both (api-spec 7).
3. **A3 says "a role table and a lookup" and nothing about how a caller proves who it is.** Closed (api-spec 2): opaque bearer tokens, 32 random bytes, stored as SHA-256, made once by `flowstat user add`, compared in constant time. No passwords, sessions or JWT; the random bytes are produced at the edge, never in a lower layer.
4. **"Restrict publishing to designers" does not say what the admin may do.** Closed (api-spec 3): the role that writes workflows publishes them, and the admin, who has every permission, can too; an operator gets 403.
5. **The `role` of an approval step (`chief_statistician`) is a free string, not a platform role.** DR-04 needs it to mean something. Closed: users have *titles* beside their role; answering an approval needs `runs:decide` and the title the step names (an admin may answer any). The answer is recorded with the user's name.
6. **FastAPI's own 422 body is not the error format of the command line.** Closed (api-spec 4): one envelope for every non-2xx response, with `code`, `message`, `field` or `line`/`column`; FastAPI's validation error is replaced; the diagnostics of the compiler keep their codes and positions.
7. **A SQLite connection is bound to the thread that made it, and `:memory:` is private to a connection.** FastAPI runs endpoints in a thread pool and runs are driven in other threads. Closed: a connection is opened per request and per driver from the path; the API tests use a file in `tmp_path`; a test starts runs from several threads at once and expects no "database is locked".
8. **The runner returns when only waiting steps are left; nothing stays in memory.** An answer to an approval is therefore "recover from the log, signal, drive again", which is what `flowstat resume --decision` does inline and for all waiting steps at once. Closed: this becomes `RunService.decide(run_id, step, decision, by)` for one step, used by the command line and the API (api-spec 5). One driver per run: a lock per run id in the app, and the unique (run, seq) of the log underneath.
9. **Approval answers are not checked (carried over from M5).** The command line accepts any `--decision` string and any step. Closed in the same function: the step must be waiting, the decision must be one the step declares (`decisions` or the default of the action), and the caller must hold the title; the command line gets the first two checks and keeps working without users.
10. **The compiled plan has no serialised form.** `get_plan` recompiles the stored text with the stored snapshot. Closed: the deployed copy is that text and snapshot, byte for byte, with their SHA-256 in a manifest that the service checks at start; the compiler is deterministic, so the plan is the same, and a test compares the two plans. No new format.
11. **There is no Docker daemon in this environment** (the client is installed, the socket is not), and the Windows runners of CI cannot run Linux containers. Closed: the process launcher (uvicorn on 127.0.0.1) is the path that is tested everywhere, as the Proposal planned; the container launcher is behind the same interface and is tested against a fake client (the calls it makes) plus one test marked `docker` that is skipped without a daemon. The review of M6 will say that the container was not built or run here unless it is run on a machine with Docker, and `scripts/` gets a command for that.
12. **NFR-07 says no operating-system calls outside the packager.** Nothing enforces it today. Closed: an architecture test allows `subprocess`, `socket` and `docker` only in `deploy/`, so the rule is checked and not only written. (`subprocess`, `socket` and `docker` are imported nowhere in `src` today.)
13. **A deployed service needs to be called by an external system and has no users table.** Closed (api-spec 2 and 7): one key per deployment, made when it is deployed, shown once, stored as a SHA-256 in the manifest; it has the permissions of `operator` and nothing else.
14. **"The same results as the core's executor" is not defined.** Closed (api-spec 7): the final state, error code and output of every step, and the outcome, equal for the same version, inputs, input files and answers; times and run ids may differ. The acceptance test runs the example workflow both ways on the synthetic forms and compares the two reports step by step.
15. **A launcher has races: a port that is taken, a process that is not ready, a process left behind when a test fails.** Closed: the port is found by binding port 0 at the edge and passed in; readiness is `GET /health` polled with an injected clock and sleep and a limit of 20 s; the process is terminated in a `finally`, and a failure marks the registry row `failed` with the last lines of the log.
16. **A contract that is not checked drifts.** Closed: the OpenAPI documents of the core and of the service are golden files; a test walks every route and requires a declared permission (or `public`), then calls it as each of the roles admin, designer and operator and without a token, and compares the status with the table of `api-spec.md` section 3, which the test reads from the document (NFR-08: no route without a test for each role).
17. **A client must write `version: N` in the text to match the number the store gives** (E-VER-001 at publish), and has no way to know N before saving. Closed in the client flow of the spec: `GET /workflows/{name}/versions` gives the numbers; the response of the save names the number and the error of publish says what to change. No new endpoint.
18. **Tests of an asynchronous API are flaky or slow if they sleep.** Closed: the app takes its executor as an argument; tests use one that runs the run before returning (and a real thread pool in the concurrency test), and the clock and ids are injected.
19. **What happens to runs when the server stops is not decided.** Closed (api-spec 5): the app stops accepting, waits for the runs in flight for a limit, and leaves the rest in the log as they are; `flowstat resume` takes them up; resuming all at start is M8.

Left out on purpose: user-management endpoints, passwords, TLS, CORS (all in M7 or in front of the server), rate limiting, token rotation, the outbox and ingest (M7, US-31), resuming at start and the epoch fence (M8), more than one core process. The tests of this milestone are written before the code they test where the code is not trivial glue (the permission walk, the equivalence test and the decision checks first), although the rule requires it only for C1, C3, C4 and C6.

## Review

Delivered against the goal: an external system and a person can use the engine over HTTP, with roles, and a published version can be deployed as a separate service that gives the same results. `flowstat user add` makes a user and prints a token once (only its SHA-256 is stored). Every route declares a permission and a test calls each route as each role and without a token against the table of `api-spec.md`; an operator who publishes gets 403 `E-AUTH-002` and nothing changes. `POST /workflows/{name}/runs` answers 202 with a run id; invalid inputs give 422 with one error per input; the approval is answered with `POST /runs/{id}/decisions`, checked in a fixed order (the step waits, the decision is declared, the person holds the title the step names, DR-04). An admin deploys a version: a bundle with a SHA-256 manifest, a service that refuses a changed file, started as a process or as a container, and its reports equal those of the core in four scenarios.

| --- | --- | --- | --- |
| US-29 roles | A3 | 3 | `tests/unit/api/test_contract.py`, `tests/unit/service/test_permissions.py`, `tests/acceptance/test_us29.py` |
| US-25 runs over REST | B4 | 5 | `tests/unit/api/test_runs.py`, `tests/unit/service/test_decide.py`, `tests/acceptance/test_us25.py` |
| US-30 deploy as a service | B5 | 13 | `tests/unit/deploy/`, `tests/unit/api/test_service.py`, `tests/acceptance/test_us30.py` |

Measurements: 1,656 tests (1,655 where the container test skips), 96.8% coverage (gate 90%), CI green on Linux and Windows for every story. Golden OpenAPI files for the core and the service. A request costs 2 to 9 ms in the app, a run to its approval 75 ms, a process deployment 0.4 to 0.6 s (`research/api-measurement.md`). The list of runs cost 5.5 ms per stored run because every report compiled the plan again; it now reads the status from the events (see the note).

What was and was not verified: the process path was run for real everywhere (a uvicorn process, a run, an approval, the stop). The container path was first written against a fake Docker client, because the sandbox has no daemon; the test that builds the image and runs the container then ran on the Ubuntu runner of CI and passed, and it skips on the Windows runner (Windows containers only). The container path was therefore not run on the machine where it was written, and its time was not measured.

DR-04 holds in a deployed service too: a deployment makes one key that starts runs and one key per title that an approval names; the first cannot answer an approval. (The first version of US-30 had one key for everything; it was changed before the tag, see the journal.)

## Retrospective

- Worked: the audit again, with nineteen gaps on paper. Three of them changed the design before any code: both apps live in `api` and `deploy` only packages and launches; the answer to an approval is "recover, signal, drive" in one service function; the plan has no stored form, so a deployment freezes the text and the snapshot with hashes. None of the stories needed a change of design afterwards, except the one below.
- Worked: giving the service the same code as the core. The service keeps its frozen version in its own SQLite file as a published version with its number, so it uses the same services and the same run functions; the equivalence test then found only one real difference (who answered the approval), and not a drift.
- Worked: the walk of the routes. The permission is declared on the route and the test reads the document that FastAPI generates, so a new route without a permission fails a test the day it is added.
- Went wrong: the layer rules. I wrote the entry point of the core in `api` and it imported `deploy`; the architecture test refused (two packages of one layer). The fix was a layer 9 package `serve` that only wires the two, and `service/deployments.py` that takes the packager and launchers as arguments. The rules did their job; the audit had decided that `deploy` would not import `api` and had not decided who joins them.
- Went wrong: the first reading of "the same results". The test failed on the output of `approve`, which names who answered. It is a real difference, not a bug; the contract now says what may differ (times, run ids, the name that answered), and the test names the expected outcome of each scenario so that two equally wrong runs cannot agree.
- Went wrong: the container test failed on the Windows runner. The runner has a Docker daemon, in Windows-container mode, which cannot pull a Linux image. The launcher reported it correctly, as a 409 with the reason; the test did not expect a daemon that cannot help and now skips on a non-Linux one. On the Ubuntu runner the image was built and run for the first time anywhere.
- Went wrong, found by reading my own review: the first version of US-30 gave a service one key that could answer every approval, which undid DR-04 inside a service. It was written down as a limit; it should have been a defect. Fixed before the tag: a key per title, so starting a run and answering its approval are different keys, and the test of the service checks that the first is refused.
- Went wrong: `httpx` was named as the test client in the extras, but the current Starlette uses `httpx2`; found when mypy saw two `Response` types. Corrected, together with the `actions` extra, which listed `httpx` for an action that uses `urllib`.
- Cost that should be said plainly: a plan is still compiled for every report (8 ms), because the plan has no stored form; an app that is stopped leaves its unfinished runs in the log and nothing resumes them until M8; deployed services are separate processes that the core does not watch, so a row can say `running` after a machine restart.
- Velocity: 21 SP planned and delivered. The work not in the plan was the layer 9 package, the sharing of the driving code with the command line (`service/driving.py`), the `user` commands, and the check of an answer in the command line.
- Next: M7 (IDE and event ingest) needs CORS and the ingest of the events of services (US-31). Carried forward: a cache of the compiled plan of a published version (M8), resuming unfinished runs at start (M8), a host allowlist for `http.call` (M8), the timeout of a waiting step (M9). The tag `m6` is to be created on `main` after this is merged.
